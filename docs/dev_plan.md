# 开发计划

## 1. 目标与交付标准

开发目标是按既定顺序稳定完成蚂蚁庄园和蚂蚁森林日常任务，并解决旧实现中的页面卡死、误触、步骤不原子、Resume能力不足和排查困难问题。

最终交付应满足：

- 庄园按“主页、家庭、领饲料”执行。
- 森林按“收自己能量、偷好友能量及抽奖、浇水、能量雨”执行。
- 每个动作都有前置条件和完成验证。
- 未知页面不继续猜测点击，并能执行有限恢复。
- 中断后能根据本地运行状态和支付宝真实页面安全恢复。
- 每次运行均有结构化日志，关键异常有对应截图。
- 能量雨经过真机延迟测试和多轮得分验收。

## 2. 旧项目复用原则

旧项目 `AutoPorcessAntMandorAndForestTasks` 可以提供经过真机或离线测试的基础能力，但不整体复制旧Workflow。迁移时先补测试，再适配当前组件边界。

### 可优先迁移

| 旧实现 | 新位置 | 处理方式 |
| --- | --- | --- |
| `device/adb.py` | `src/device_bridge/adb` | 保留设备发现和基础命令，增加性能指标与持久连接能力 |
| `domain/models.py` | `src/domain_data` | 精简并补充页面、弹窗和步骤结果模型 |
| `perception/ui_tree.py` | `src/screen_perception` | 迁移解析与元素查询，并保留离线Fixture测试 |
| `perception/vision.py` | `src/screen_perception` | 迁移模板匹配和歧义拒绝逻辑 |
| `actions/executor.py` | `src/action_executor` | 保留页面、元素和坐标安全校验，加入动作后验证 |
| `runtime/errors.py`、`wait.py` | `src/runtime`、`src/state_machine` | 迁移有限等待、超时和错误类型 |
| `evidence/recorder.py` | `src/logger` | 只迁移日志和截图记录能力，输出到当前目录规范 |
| `services/quiz_solver.py` | `src/web_search` | 迁移搜索、答案判断和缓存测试 |
| `tests/fixtures`和模板图片 | `tests`、`screenshots/template` | 逐个确认仍与当前支付宝页面一致后复用 |

### 需要改造后复用

- Observation采集需要拆为快速观测和完整观测，避免每次都执行耗时的UI dump。
- PageDetector需要从单一页面枚举改为“底层页面加弹窗Overlay”，减少新弹窗导致的UNKNOWN。
- 庄园、森林和抽奖Workflow只复用已验证的页面规则与动作片段，业务顺序按当前需求重组。
- 模板和固定坐标必须用当前手机重新校准，并支持分辨率换算。

### 仅作参考，不直接迁移

- 逐次PNG截屏并对每个目标分别执行ADB点击的能量雨循环。
- 固定寻找特定好友的能量雨赠送逻辑。
- 未经过真机验证的森林、抽奖和外部广告完整流程。
- 页面未知后继续使用固定坐标的处理方式。

## 3. 建议开发顺序

### 阶段0：工程基础

建立Python工程配置、依赖管理、CLI入口、配置加载、错误模型、日志格式和测试命令。

验收结果：

- 可以执行`doctor`检查ADB、FFmpeg、scrcpy、配置和输出目录。
- 单元测试、代码检查可以使用统一命令运行。
- 密钥、本机配置、日志、Resume数据和运行截图不会进入Git。

### 阶段1：设备桥接与实时链路验证

先实现`device_bridge/common`和`device_bridge/adb`，再做`device_bridge/realtime`技术验证。这一阶段提前处理能量雨的最大技术风险，不等待全部业务完成。

主要工作：

- 设备发现、截图、UI dump、点击、滑动、返回和应用启动。
- 统一截图、视频帧和设备坐标。
- 测量ADB截图、单次点击、连续点击的P50和P95延迟。
- 接入scrcpy视频流，测量帧率、画面延迟和触控延迟。
- 用森林录屏离线验证能量球识别，用真机验证点击命中率。

验收结果：输出一份延迟报告，并明确能量雨采用ADB输入还是scrcpy控制通道。

### 阶段2：领域模型与页面感知

实现`domain_data`和`screen_perception`，建立可离线回放的识别链路。

主要工作：

- 定义Observation、Page、Overlay、Element和识别依据。
- 实现快速观测与完整观测。
- 迁移UI Tree解析、模板匹配和基础视觉检测。
- 为每个真实页面保存截图、XML和期望识别结果。
- 区分页面加载中、已知弹窗和真正UNKNOWN。

验收结果：已有Fixture可离线稳定识别，歧义目标会被拒绝。

### 阶段3：安全执行、状态机与Resume

实现`action_executor`、`state_machine`、`workflow/recovery`以及`src/runtime`中的运行状态读写。

每个原子步骤统一执行：

```text
探测 -> 校验前置状态 -> 执行一个动作 -> 验证后置状态 -> 保存结果
```

恢复顺序为重新观察、关闭已知弹窗、安全返回、重进任务入口、重新探测完成状态，超过预算后失败。

验收结果：通过模拟崩溃、ADB断开、弹窗插入和页面加载超时测试；恢复时不会重复执行已经完成的捐蛋等不可逆动作。

### 阶段4：庄园主页

依次实现多次打赏、条件性带小鸡回家和每日贴贴小鸡。

验收结果：分别覆盖无打赏、多次打赏、小鸡在家、小鸡外出和日记已完成状态，并在真机上连续运行验证。

### 阶段5：庄园家庭

依次实现捐蛋、请客和喂食。每个任务从家庭任务页重新探测状态，完成后验证`(1/1)`、`明天再来`或对应时间提示。

验收结果：任务已完成时可重复运行；资源不足时明确报失败；中断恢复不会重复捐蛋。

### 阶段6：公共广告与抽奖能力

在`workflow/shared`实现庄园和森林共用能力：

- 需要滑动才能计时的15秒广告。
- 纯等待的视频任务。
- “猜价格”弹窗和其他已知干扰弹窗。
- 每日签到、领取、兑换、重复广告和抽奖。
- 动态活动换皮下基于任务文字和结构的识别。

验收结果：广告计时器缺失时可以重进；弹窗出现时可以恢复；每次领取后重新读取次数。

### 阶段7：庄园领饲料

先实现签到、答题、视频和杂货铺，再接入抽抽乐与IP抽抽乐，最后实现芭芭农场、小鸡厨房和连续刷新的外部浏览任务。

主任务完成后的普通饲料奖励不领取；签到和推进任务链所需的领取仍按规则执行。

验收结果：每个子任务独立真机通过后再加入完整领饲料Workflow，动态未出现的可选任务记为SKIPPED。

### 阶段8：森林常规任务

依次实现：

- 收取自己的普通能量和延迟出现的签到气泡。
- 好友页面的一键收循环，直到进入森林寻宝广告。
- 右侧、左侧两个森林抽奖。
- 真爱合种100g和普通合种520g。

验收结果：好友数量变化不会破坏循环；森林抽奖完成后能可靠返回主页；浇水资源不足时报失败。

### 阶段9：能量雨正式实现

基于阶段1的技术验证完成实时执行器：

- 只在游戏阶段启用实时点击。
- 检测并跨帧跟踪能量球，估计移动速度。
- 根据端到端延迟点击预测位置。
- 对同一能量球去重，并支持一帧多个目标。
- 识别结果页后立即停止点击。
- 第一轮结束后赠送第一个好友，再完成第二轮。

验收结果：记录帧率、延迟、检测数、点击数、空点数和最终得分；多天、多轮结果达到约定命中率后才并入完整Workflow。

### 阶段10：全流程与稳定性

按最终业务顺序串联庄园和森林，重点验证任务已完成、任务未出现、随机弹窗、网络慢、ADB断开和程序重启。

完成标准：

- 连续多日完整运行成功。
- 必需任务失败时停止并给出准确原因。
- 任一失败都能通过日志中的截图文件名定位页面。
- 相同失败页面加入Fixture后可以离线复现。
- Resume不会重复执行不可逆任务。

## 4. 测试策略

- 单元测试：坐标换算、UI Tree、模板匹配、状态转换和搜索结果解析。
- 回放测试：使用固定截图和XML验证页面识别及Workflow决策，不连接手机。
- 设备探针：只执行一个页面或一个动作，生成校准数据，不运行完整任务。
- 子任务真机测试：每个任务独立验收成功、已完成和异常分支。
- 每日端到端测试：最后阶段才运行庄园与森林完整流程。

发现新页面时先保存素材、补识别测试，再增加处理规则，不在Workflow中临时加入未经验证的坐标点击。
