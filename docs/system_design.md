# 蚂蚁庄园与蚂蚁森林自动化系统设计

## 1. 目标与范围

系统在 WSL 中运行，通过 ADB 控制 Android 手机，自动完成支付宝蚂蚁庄园和蚂蚁森林中规则固定的日常任务。

当前运行边界是单机、单设备、人工触发的一次执行。Windows 只负责将 USB 设备共享给 WSL；任务判断、设备控制、日志和截图均在 WSL 中完成。

具体任务、操作例外和录屏索引见[支付宝每日任务文字描述](../screenshots/demo/支付宝每日任务文字描述.txt)。本文定义实现这些任务时的组件边界和执行约定。

| 项目 | 已确认的约定 |
| --- | --- |
| 设备连接 | Windows USB Share/Attach 到 WSL，由 WSL 内 ADB 控制；不支持无线和多设备 |
| 小课堂 | 初期固定选择一个选项，不接入网页搜索；答错也算完成 |
| 调试方式 | 单独运行任务模块或具体任务，逐步进行真机验证 |
| 失败处理 | 一旦判定任务失败，立即结束本次运行，不继续后续任务 |
| 开发流程 | 在 `dev` 分支开发，测试通过后合并到 `main` |

系统不追求成为通用 Android Agent。支付宝当前页面是事实来源，程序只执行经过识别和验证的确定性动作。

## 2. 核心原则

每个步骤遵循同一个闭环：

```text
观察页面 -> 识别状态 -> 决定动作 -> 执行动作 -> 验证结果
```

- 不按录屏坐标和固定等待时间机械回放。
- 每次只执行一个可验证的原子动作。
- 页面未知或目标不确定时停止点击。
- 所有循环都有次数和时间上限。
- 恢复后重新读取支付宝状态，不盲目沿用旧坐标。
- 必需任务资源不足或无法验证时，本次运行报失败。
- 捐蛋、浇水、兑换、抽奖等动作结果不明时，先核实是否已生效，不能直接重复提交。

能量雨是实时控制例外：游戏内使用视频帧和低延迟触控闭环，不为每个点击等待一次 ADB 截图；进入游戏和结束结算仍需验证。

## 3. 总体结构

```text
CLI -> runtime：组装组件、选择任务、保存进度
         -> workflow：业务顺序、完成条件、恢复策略
              -> state_machine：步骤状态、超时和重试预算
              -> screen_perception -> device_bridge：获取与识别页面
              -> action_executor
                   -> device_bridge：发送输入
                   -> screen_perception：获取动作后的新观测并验证

domain_data：组件共用类型
logger：记录各组件的动作、状态和诊断信息
runtime/：由 runtime 组件管理的运行数据
```

普通页面使用 ADB 截图、UI Tree 和 ADB 输入。能量雨使用独立的实时视频与低延迟触控通道，但仍通过同一台 ADB 设备建立连接。

UI Tree 在自绘页面可能不可用，此时通过截图识别。能量雨实现可参考 `real-device-regression` 分支，仍需在当前设备上验证延迟和效果。

## 4. 组件职责

### `src/device_bridge`

隔离所有手机通信细节。

- `common`：设备接口、坐标、边界、屏幕尺寸和方向换算。
- `adb`：截图、UI dump、点击、滑动、返回、启动应用和前台页面查询。
- `realtime`：scrcpy 视频流、H.264 解码、低延迟触控和延迟统计。

上层组件不能直接执行 ADB 或 scrcpy 命令。

### `src/domain_data`

存放不依赖具体实现的 Python 类型定义，不存放运行时文件。

| 模型 | 主要内容 |
| --- | --- |
| `Observation` | 观测编号、截图/UI Tree 各自的采集时间、设备尺寸、方向、前台信息和识别结果 |
| `Page` | 底层页面类型、识别依据和可信度；无法确认时为 `UNKNOWN` |
| `Overlay` | 弹窗类型、区域、遮挡关系和可识别的关闭入口；支持多个覆盖层 |
| `Element` | 文字或语义、边界、坐标系、所属观测编号和识别证据 |
| `ObservationEvidence` | UI Tree、OCR、模板或视觉特征的来源、原始结果和分数 |
| `WaitCondition` | 预期出现或消失的状态、稳定要求、轮询间隔和超时 |
| `ActionResult` | 是否发送动作、验证结果、前后观测引用和失败原因 |
| `TaskResult` | 任务状态、完成证据、耗时和失败原因 |
| `RecoveryPolicy` | 允许的恢复动作、次数上限和总耗时上限 |

不同识别方法的分数不能直接视为同一种概率。具体页面和目标规则规定动作所需的证据组合。

### `src/screen_perception`

负责回答“当前看到了什么”，不决定业务动作。

- 解析 UI Tree。
- 识别页面和覆盖在页面上的弹窗。
- 执行模板匹配、局部文字识别和视觉检测。
- 识别并跟踪能量雨中的能量球。
- 返回识别依据和可信度。

页面和弹窗分别建模，避免一个新弹窗使整个底层页面变成 UNKNOWN。

识别分为两层：`PageClassifier` 判断底层页面，`OverlayClassifier` 判断覆盖层，再定位可操作元素。这些是组件内部职责，不新增顶层组件。底层被遮挡且无法确认时，仍应返回 `UNKNOWN`，不能根据弹窗猜测底层页面。

优先使用页面实际可用的文本和结构证据，再结合局部 OCR、模板、颜色和几何特征。活动主题和布局经常变化，单个模板命中不足以证明页面身份。前台包名也只是辅助证据：支付宝内跳转其他小程序时，包名可能不变。

截图与 UI Tree 有采集时间差，需要确认二者仍属于同一页面状态；每个元素必须关联其来源观测，供执行器检查是否过期。

### `src/action_executor`

负责安全执行动作：

1. 校验观测时效、页面身份、元素证据和弹窗遮挡情况。
2. 将截图或视频坐标转换为设备坐标。
3. 执行点击、滑动或返回。
4. 获取新观测并验证后置条件。

没有通过前置校验的动作不会发送到手机。

Workflow 定义前置条件和业务后置条件，执行器通过 `WaitCondition` 统一等待并验证，返回“未发送”“已发送但结果未确认”或“已验证成功”。等待以状态变化为依据，固定时长只作为轮询间隔或动画等待辅助。

执行器不自行重试业务点击。动作超时可能意味着已经生效，是否重试必须由 Workflow 根据新观测决定。

能量雨在该组件内使用专用实时执行路径，消费带时间戳的目标检测结果。过期帧不得继续指导点击，游戏退出或通道异常时停止实时输入。

### `src/state_machine`

提供通用状态机能力，包括状态转换、原子步骤、超时、重试次数和步骤结果。它不包含庄园或森林的具体业务规则。

Workflow 决定下一步和是否允许重试，状态机统一检查并记录预算；单次动作内的等待由执行器完成。内层循环受外层步骤总耗时限制，避免多层重试叠加造成长时间卡住。状态机不直接识别页面。

### `src/workflow`

描述业务顺序并组合状态机、感知和动作组件。

- `manor`：庄园主页、家庭和领饲料任务。
- `forest`：收自己能量、偷好友能量、浇水和能量雨。
- `shared`：庄园和森林共用的广告、抽奖等流程。
- `recovery`：等待稳定、关闭已知弹窗、安全返回、重进任务入口和重新探测任务状态。

Workflow 同时定义任务触发条件、资源需求、完成证据和允许跳过的条件。`shared` 复用广告浏览、抽奖和动态列表扫描机制，具体次数、按钮和完成条件由业务流程提供，不能将不同活动写成相同的动作序列。

### `src/web_search`（后续扩展）

初期不实现或依赖网页搜索。小课堂使用可配置的固定选项，例如 `option_index: 0` 表示第一个选项；先识别答题页面和选项区域，再点击并验证答案解析或任务完成状态，不使用固定屏幕坐标代替选项识别。

后续需要提高正确率时，再启用网页搜索、答案提取和缓存，由 Workflow 决定搜索失败后的策略。缓存写入根目录 `runtime/`。

其他外部能力以后各自建立独立组件，不集中放入通用 services 目录。

### `src/logger`

实现结构化日志记录，负责记录动作、状态转换、重试、耗时和失败原因。日志文件写入项目根目录的 `logs/`；需要截图时写入 `screenshots/runs/`，并在日志中记录截图文件名。

记录关联运行、任务和观测编号。失败信息应包含页面分类、识别证据、最后动作、预期结果和实际结果，必要时附带 UI Tree，使日志能解释“为什么点这里、为什么判定失败”。

### `src/runtime`

这是运行编排的源代码组件。它读取配置、连接设备、组装组件、创建一次运行，并负责读写 Resume 状态。CLI 只调用 Runtime，不直接包含业务逻辑。

`TaskModuleRunner` 是该组件内的任务选择与执行能力，支持完整日常流程、单模块和单任务调试。两种模式共用相同的识别、验证和失败规则。

### `runtime`

这是项目根目录下的运行数据目录，不是源代码组件。Resume 数据库、检查点、搜索缓存和进程锁等运行时文件统一放在这里，不放入 `src/`。

### `config`

位于项目根目录，保存可提交的示例配置和本机配置。密钥只通过环境变量或未提交的本机配置读取。

设备标识、等待和恢复预算、小课堂选项属于配置；文本别名、模板、识别区域和阈值归对应页面识别规则；业务完成规则归 Workflow，避免将所有规则堆入一个配置文件。

## 5. Workflow 顺序

庄园严格按以下顺序执行：

```text
主页 -> 家庭 -> 领饲料
```

森林严格按以下顺序执行：

```text
收自己能量 -> 偷好友能量及抽奖 -> 浇水 -> 天天能量雨
```

完整运行先执行庄园，再执行森林。每个任务先探测 `待执行`、`已完成`、`未出现`或`异常`，再决定执行、跳过或失败。只有任务明确允许不出现、且扫描充分时，才能跳过；识别失败不等于任务不存在。

### 关键业务约束

| 模块 | 约束和完成依据 |
| --- | --- |
| 庄园主页 | 条件触发打赏和带小鸡回家；每日贴贴小鸡以“明日再来”验证 |
| 家庭 | 每日捐 1 颗蛋、执行当前可请客任务和帮家人喂食；检查任务进度与按钮状态 |
| 领饲料 | 默认只完成任务；签到、抽奖机会、用于刷新后续任务的指定奖励需要领取 |
| 自己能量 | 动态定位能量球，单独处理延迟出现的能量签到气泡 |
| 好友能量 | 逐页收取，以寻宝页作为遍历结束证据；随后完成右侧和左侧抽奖 |
| 浇水 | 真爱合种每天 100g，合种按任务描述为 520g；提交前核对数量 |
| 能量雨 | 首轮后赠送第一个好友机会，再完成第二轮并验证结算 |

签到遇到饲料超上限提示时确认领取。具体任务例外以任务文字描述为准，不能因统一抽象而省略。

### 动态列表与重复任务

共用流程为“扫描当前视口 -> 执行一个任务 -> 验证 -> 重新扫描”。领取或返回后卡片可能移动，也可能在原位置刷新成新任务，因此每次都重新定位。

扫描记录任务身份、已见内容和滚动进度，设置最大滚动次数、无进展次数和总耗时上限。广告浏览以计时器或完成文字退出，需要滑动的广告按约定周期滑动；计时器未出现时在预算内返回重进。

循环必须有业务结束证据，例如打赏按钮消失、子任务进度达到要求或好友遍历进入寻宝页。达到循环上限只表示无法继续验证，不代表成功。

### 调试入口

以下为计划提供的 CLI 语义，具体命令在实现时确定：

```text
daily
debug --module manor_home
debug --module manor_family
debug --module manor_feed
debug --module forest
debug --task manor.family.donate_egg
```

调试只执行选定范围。任务声明入口条件和资源前提，执行前验证；缺少前提时明确失败，不自动扩展为完整日常任务。调试中的捐蛋、浇水等也会改变当日状态，必须使用同一份进度记录，并重新读取支付宝当前状态。

## 6. 原子步骤与 Resume

以每日捐蛋为例：

```text
打开项目 -> 打开确认页 -> 确认捐1颗 -> 验证家庭任务显示(1/1)
```

如果程序在确认捐蛋后退出，`runtime/`中的记录可能仍是 IN_PROGRESS。重新运行时，Runtime 读取记录，Workflow 返回家庭任务页；若页面已经显示 `(1/1)`，则更新为 SUCCESS 并继续后续任务，不会再次捐蛋。

运行记录只表示程序最后确认到哪里。恢复时仍需重新观察支付宝页面，并以支付宝当前状态为准修正本地记录，不能根据旧记录直接发送下一次点击。

进度按设备、业务日期和任务身份区分，业务日期按 `Asia/Shanghai` 计算。跨日后重新探测任务，不能直接复用前一天的完成记录。

捐蛋、浇水、饲料兑换、做美食和抽奖结果不明时，必须先找页面证据。若无法区分“已执行”和“未执行”，记录结果不明并终止，不能因本地记录缺失就重复操作。Resume 用于下一次人工启动后重新探测，不表示失败后自动重启。

常用步骤状态包括：

- `PENDING`：尚未开始。
- `IN_PROGRESS`：动作已开始，结果尚未确认。
- `SUCCESS`：已验证完成。
- `ALREADY_DONE`：执行前已经完成。
- `SKIPPED`：符合该任务明确允许的跳过条件。
- `FAILED`：任务无法完成或验证，终止本次运行。

## 7. 恢复策略

已知广告和弹窗可视为页面中断，在预算内恢复；一旦判定任务失败，立即结束本次运行。恢复发生在失败判定之前，不在失败之后继续其他任务。

遇到预期外页面时按以下顺序处理，每步都需要足够的页面证据和剩余预算：

1. 停止点击并保存当前状态。
2. 等待页面加载稳定后重新识别。
3. 从最上层关闭已知弹窗，每关闭一层都重新观察。
4. 仅在恢复策略允许的场景执行一次安全返回，再识别页面。
5. 重新进入当前任务入口并探测完成状态。
6. 无安全恢复路径、预算耗尽或无法确认结果时，记录日志和截图并立即结束运行。

恢复策略不使用“点击右上角大概位置”一类通用猜测。

其他小程序可能是预期任务目标，也可能是意外跳转，必须结合当前任务判断。未知页面不允许猜测关闭按钮或连续盲按返回。

`RecoveryPolicy` 定义允许动作、次数和总耗时，初期可将最多 2 次恢复尝试作为待真机校准的默认值。嵌套任务共享外层预算，网络等待、页面恢复和业务重试不能无限叠加。

## 8. 运行产物

```text
logs/<run-id>.jsonl
screenshots/runs/<run-id>/<index>-<reason>.png
runtime/task_state.db                 # 使用 SQLite 时
runtime/checkpoints/<run-id>.json     # 使用 JSON 检查点时
runtime/cache/                        # 搜索等运行缓存
```

`logs/`记录发生过什么；`runtime/`保存程序继续运行所需的状态；`screenshots/runs/`只保存需要排查的关键画面。示例素材和匹配模板分别保留在 `screenshots/demo/` 和 `screenshots/template/`。

状态存储初期在 SQLite 和 JSON 检查点中选择一种，避免维护两个进度来源。

源代码与运行产物的边界如下：

```text
src/          Python 实现代码
config/       配置文件
runtime/      Resume 数据库、检查点、缓存和临时运行状态
logs/         运行日志
screenshots/  示例、模板和运行截图
docs/         设计文档
tests/        测试代码与测试数据
```

## 9. 实现与验证顺序

1. 验证 USB/ADB 连接、截图、UI Tree 可用性、输入和坐标换算。
2. 用庄园主页建立页面识别、弹窗处理、动作验证和失败日志闭环。
3. 按单任务逐步验证家庭、领饲料和森林流程，再组合完整顺序。
4. 独立验证能量雨的视频延迟、目标跟踪、触控和结算。
5. 验证弹窗中断、意外跳转、重复启动、提交动作后中断等场景，再进行完整日常回归。

录屏和截图用于验证识别规则及典型页面；真机用于验证跳转、完成状态和恢复效果。点击命令执行成功不等于任务完成，完成必须有页面证据。
